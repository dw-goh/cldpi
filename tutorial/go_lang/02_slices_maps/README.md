# 02 — 슬라이스와 맵

**이 장이 이 튜토리얼에서 가장 중요하다.** Go 초보가 내는 버그의 절반은 슬라이스에서 나온다. 문법이 어려워서가 아니라, Python의 list처럼 생겼는데 동작이 다르기 때문이다.

```bash
go test -v ./02_slices_maps/
```

## 배열과 슬라이스는 다른 타입이다

```go
var a [5]int      // 배열 — 길이가 타입의 일부다. [5]int와 [6]int는 다른 타입
var s []int       // 슬라이스 — 길이가 타입에 없다
```

배열은 값 타입이라 대입/전달할 때 **전체가 복사된다** (C의 구조체 배열처럼). 실무에서 직접 쓸 일은 드물다. 우리가 쓰는 건 거의 전부 슬라이스다.

슬라이스는 실제로 이렇게 생긴 3워드 구조체다:

```
┌─────────┬─────┬─────┐
│ ptr     │ len │ cap │
└────┬────┴─────┴─────┘
     │
     ▼
   [0][1][2][3][4]...   ← 실제 데이터가 사는 배열 (backing array)
```

**여기서 모든 혼란이 나온다.** 슬라이스를 함수에 넘기면 이 3워드는 복사되지만 `ptr`이 가리키는 배열은 공유된다. 그래서:

- 원소를 고치면(`s[0] = 1`) 호출한 쪽에도 보인다 → **문제 2**
- `append`로 길이를 늘리면 호출한 쪽에는 안 보인다 (len은 복사본이므로)
- 그런데 cap에 여유가 있으면 append가 **남의 데이터를 덮어쓴다** → **문제 3**

### len과 cap

```go
s := make([]int, 3, 10)   // len=3, cap=10
s = s[:2]                 // len=2, cap=10  ← cap은 안 줄어든다
s = s[1:]                 // len=1, cap=9   ← 앞을 자르면 cap도 준다
```

`append`는 이렇게 동작한다:

```go
if len(s) < cap(s) {
    // 남는 자리에 그냥 쓴다. 새 배열을 만들지 않는다.  ← 위험 지점
} else {
    // 더 큰 배열을 새로 할당하고 전부 복사한다.
}
```

그래서 `append`의 반환값을 **반드시 다시 대입해야 한다**. `append(s, v)`만 쓰고 버리면 아무 일도 안 일어난 것처럼 보인다.

```go
s = append(s, v)   // ○
append(s, v)       // ✗ 컴파일 에러 (반환값을 안 씀)
```

## 맵

```go
m := make(map[string]int)      // ○
var m map[string]int           // nil 맵 — 읽기는 되지만 쓰면 panic
m := map[string]int{"a": 1}    // 리터럴

v := m["없는키"]                // panic 아님. 제로값 0
v, ok := m["없는키"]            // ok로 존재 여부 확인
delete(m, "a")
len(m)
```

**맵의 순회 순서는 무작위다.** 버그가 아니라 의도된 설계다. 순서에 의존하는 코드를 못 짜게 하려고 런타임이 매번 시작점을 랜덤하게 잡는다. 정해진 순서가 필요하면 키를 뽑아서 정렬해야 한다 → **문제 7**

맵은 슬라이스와 달리 **항상 참조처럼 동작한다.** 함수에 넘겨서 쓰기를 하면 호출한 쪽에도 그대로 보인다.

## 문자열은 바이트 슬라이스다

```go
s := "안녕"
len(s)        // 6  ← 문자 수가 아니라 바이트 수
s[0]          // 236 (byte) ← 문자가 아니다
s[0:1]        // 깨진 문자열 (UTF-8 시퀀스 중간을 잘랐다)

for i, r := range s {
    // i는 바이트 오프셋, r은 rune(int32). 0,'안' 다음이 3,'녕'
}
[]rune(s)     // 문자 단위 슬라이스로 변환. len은 2
```

Python 3의 `str`(코드포인트 시퀀스)과 다르고, C의 `char*`(널 종료 없음, 길이를 들고 다님)와도 다르다. **UTF-8 바이트 열 + 길이**라고 생각하면 된다.

> 이건 나중에 M3의 "유니코드 정규화(NFC/NFD)" 항목에서 다시 나온다. macOS는 파일명을 NFD로, 리눅스는 NFC로 저장해서 "같은 이름인데 바이트가 다른" 문제가 생긴다.

## 걸려 넘어지기 쉬운 곳

**문제 3이 이 장의 핵심이다.** 정답은 한 줄이지만, 왜 필요한지 이해하는 게 중요하다.

```go
return append(dst[:len(dst):len(dst)], v)
//                    └─ high ─┘└─ max ─┘
```

`s[low:high:max]`에서 세 번째 숫자가 cap을 정한다. `max == high`로 만들면 `cap == len`이 되어 append가 무조건 새 배열을 할당한다. 그러면 원본을 건드릴 수 없다.

이 패턴은 라이브러리 함수가 **호출자가 준 슬라이스에 append할 때** 쓴다. 지금은 억지스러워 보여도, M1에서 수신 버퍼를 잘라 쓸 때 똑같은 상황이 나온다.

**문제 4 — `dst := src`는 복사가 아니다.** 배열을 공유한다. `make` + `copy`를 써야 한다. (Go 1.21+에는 `slices.Clone`이 있지만, 여기서는 `copy`를 직접 써보자.)

**문제 7 — 테스트가 20번 반복 실행한다.** 정렬을 빼먹으면 한두 번은 우연히 통과할 수 있어서다.

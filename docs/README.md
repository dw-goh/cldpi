# docs 문서 지도

> `cldpi` 프로젝트 문서의 인덱스. **작업 전에 어떤 문서를 봐야 하는지** 여기서 먼저 찾는다.
> `cldpi`는 라즈베리파이5 + SSD 위에서 동작하는 단일 사용자 개인 클라우드 스토리지(CAS 저장 + 자체 바이너리 프로토콜 + FUSE 마운트)다.

---

## 문서별 역할 — 이럴 때 이 문서를 본다

| 문서 | 한 줄 역할 | 이럴 때 참고한다 |
|---|---|---|
| [`PRD.md`](./PRD.md) | **무엇을·왜** (제품 요구사항) | 목표·범위·범위 외, 대상 사용자, 사용자 시나리오, 기능/비기능 요구사항, 성공 지표, 향후 고려 과제를 확인·수정할 때 |
| [`ARCHITECTURE.md`](./ARCHITECTURE.md) | **어떻게** (기술 설계) | CAS 구조, 계층 분리, 저장소/SQLite 스키마, 프로토콜(프레임·opcode·에러코드), 보안(경로 격리·mTLS·페어링), FUSE 콜백, 프로젝트 구조·바이너리 이름을 구현·확인할 때 |
| [`PLAN.md`](./PLAN.md) | **언제·어떤 순서로** (실행 계획) | 마일스톤(M0~M6)·완료 조건(DoD)·작업 목록·시간 견적, 실행 리스크, 운영 원칙, 착수 전 체크리스트를 볼 때. "지금 무엇을 만들 차례인가"를 판단할 때 |
| [`fuse.md`](./fuse.md) | FUSE 개념 학습 노트 | FUSE가 무엇인지, 유저공간 파일시스템의 이유, 구성요소(fuse.ko·libfuse·데몬)를 이해할 때 (구현 스펙이 아니라 배경 지식) |
| [`devlog/devlog.md`](./devlog/devlog.md) | 개발 일지(시간순) | 지금까지 무엇을 시도했고 왜 그랬는지, 어떤 문제를 어떻게 풀었는지 맥락을 파악할 때. **작업을 진행하면 새 항목을 여기에 시간순으로 추가한다.** |

## 빠른 판단 기준

- "이 기능을 왜/무엇을 만드나?" → **PRD.md**
- "이걸 어떻게 구현하나? 스키마/프로토콜/규칙은?" → **ARCHITECTURE.md**
- "지금 무엇을 할 차례이고 완료 기준은?" → **PLAN.md**
- "FUSE 개념 자체가 헷갈린다" → **fuse.md**
- "예전에 이거 왜 이렇게 했더라?" → **devlog/devlog.md**

## 문서 간 관계

- **PRD → PLAN**: PRD는 상세 일정·마일스톤·실행 리스크를 PLAN.md로 넘긴다(단방향 포인터).
- PRD / ARCHITECTURE / PLAN 세 문서는 서로를 읽지 않아도 각자 완결되도록 작성돼 있다. 역할만 다르다: PRD=무엇/왜, ARCHITECTURE=어떻게, PLAN=언제.
- `fuse.md`, `devlog/devlog.md`는 다른 문서에 의존하지 않는 독립 노트다.

## 문서를 수정할 때 주의

- **네이밍 일관성**: 프로젝트명 `cldpi`, 바이너리는 CLI `cldpi` / 서버 `cldpi-server` / FUSE 데몬 `cldpifs`, 마운트 포인트 `~/cldpi`, 프로토콜 MAGIC `"CLDP"`. 세 핵심 문서(PRD/ARCHITECTURE/PLAN)는 이 이름으로 통일돼 있으니 다르게 쓰지 않는다.
- **역할 경계 유지**: 제품 요구사항은 PRD, 구현 방법은 ARCHITECTURE, 일정·마일스톤·실행 리스크는 PLAN에만 둔다. 한 문서에 다른 역할이 섞이면 이 지도의 판단 기준이 무너진다.

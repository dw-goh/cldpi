# cldpi — PRD (제품 요구사항 정의서)

> 라즈베리파이5 기반 개인 클라우드 스토리지. "파인더에서 열고 고치고 저장하면 끝" — 구글 드라이브급 사용 경험을 자체 인프라로.

---

## 1. 배경 & 목표

개인 문서/사진/영상을 외부 상용 클라우드에 맡기지 않고, 집에 둔 라즈베리파이5 + SSD에 저장하면서도 **구글 드라이브처럼** 쓰는 것이 목표다. 동기화 폴더를 신경 쓰거나 웹에 업로드하는 절차 없이, 운영체제 파일 탐색기에서 바로 열고 편집하고 저장하면 서버에 반영되어야 한다.

- **최우선 목표:** 파인더/탐색기에서 마운트된 폴더(`~/cldpi`)를 열어 파일을 열고, 수정하고, 저장하면 자동으로 서버에 새 버전이 반영된다.
- **부수 목표:** 버전 관리·증분 업로드·중복 제거·무결성 검증·업로드 재개를 저장 구조(CAS) 자체에서 얻는다.
- **학습 목표:** Go, 자체 바이너리 프로토콜, TLS/mTLS, FUSE 파일시스템을 직접 구현하며 시스템 프로그래밍을 익힌다.

## 2. 확정된 기술 결정

| 항목 | 결정 |
|---|---|
| 언어 | Go |
| 하드웨어 | Raspberry Pi 5 (RAM 8GB) + SSD 256GB |
| 통신 | TCP + 자체 바이너리 프로토콜 (TLS 1.3 위에) |
| 저장 | CAS(Content-Addressed Storage) + SQLite 메타데이터 |
| 버전 관리 | CAS의 부산물로 획득 (append-only) |
| 클라이언트 | CLI + FUSE 마운트 (읽기 → 쓰기 단계적) |
| 마운트 라이브러리 | `cgofuse` (macOS/Windows/Linux 공통) |
| 인증 | 기기별 Ed25519 키 + 챌린지-리스폰스 (mTLS) |
| 외부 노출 | 1단계 Tailscale 사설망 → 이후 포트포워딩은 선택 |

### 구성 요소 이름
- `cldpi` — 클라이언트 CLI (순수 Go, 크로스 컴파일)
- `cldpi-server` — 파이에서 실행하는 서버
- `cldpifs` — FUSE 마운트 데몬 (cgo 의존, OS별 빌드)

## 3. 대상 사용자

- 단일 사용자(본인). 여러 개인 기기(맥북, 데스크탑, 윈도우 PC)에서 접근.
- 기술 이해도가 있어 CLI 페어링·마운트 설정을 직접 수행할 수 있는 사용자.

## 4. 범위 (What we build)

| 영역 | 내용 |
|---|---|
| 저장 | CAS + SQLite 메타데이터, 자동 버전 관리, 휴지통, GC |
| 통신 | TCP 위 자체 바이너리 프로토콜, TLS 1.3 + mTLS, 요청 다중화 |
| 인증 | 기기별 Ed25519 키 + 챌린지-리스폰스, 6자리 코드 페어링 |
| 클라이언트 | `cldpi` CLI (push/pull/ls/mkdir/mv/rm/stat/versions/restore/trash) |
| 마운트 | `cldpifs` FUSE 마운트 — **읽기 전용 → 쓰기 가능** 단계적 |
| 외부 노출 | 1단계 Tailscale 사설망 |

## 5. 범위 외 (Non-goals, 의도적 제외)

- 웹 UI / 모바일 앱 (HTTP 게이트웨이가 전제 — 추후 선택 과제)
- 양방향 동기화 데몬 (FUSE 마운트가 이 역할을 대신함)
- 저장 암호화(at-rest), E2E 암호화
- 다중 사용자 / 공유 링크
- 완전한 POSIX 파일시스템(mmap, DB 파일, 하드링크, offset 단위 원격 쓰기 등)
  → 목표는 **"구글 드라이브급"**(문서/사진/영상)에 한정한다.

## 6. 핵심 사용자 시나리오

1. **최초 페어링:** 파이에서 `cldpi-server pair`로 6자리 코드 발급(5분 유효) → 노트북에서 `cldpi pair --server pi.tailnet --code 384921` → 클라이언트가 Ed25519 키쌍 생성, 서버에 공개키 등록. 이후 비밀번호 없이 자동 인증.
2. **CLI로 올리기/받기:** `cldpi push report.pdf` / `cldpi pull`. 연결이 끊겨도 재시도 시 이미 올라간 청크는 건너뛰고 남은 것만 전송.
3. **마운트해서 읽기:** `~/cldpi`를 열면 전체 트리가 보이고, PDF 더블클릭 시 미리보기가 뜬다. `ls`가 답답하지 않다.
4. **마운트해서 쓰기:** 파인더에서 파일을 드래그해 넣거나, 워드로 열어 수정·저장하면 새 버전이 자동 생성된다. 이름 변경/삭제도 즉시 반영.
5. **버전 복원:** `cldpi versions report.pdf`로 이력 확인 → `cldpi restore report.pdf <version>`으로 이전 버전 되돌리기.
6. **오프라인 저장:** 연결이 없을 때 저장한 변경분도 업로드 큐에 쌓였다가 재연결 시 자동 반영된다.

## 7. 기능 요구사항

### FR-1 저장 & 버전 관리
- 파일은 4MiB 고정 청크로 분할, 각 청크는 SHA-256 해시로 식별·저장(CAS).
- 파일 수정 시 새 manifest를 생성하고, 옛 버전은 append-only로 보존한다.
- 삭제는 휴지통(soft delete). 실제 blob 회수는 별도 GC 명령으로만 수행한다.

### FR-2 전송 효율
- 업로드 전 서버에 보유 청크를 조회해 **없는 청크만** 전송한다(증분·재개·중복 제거).
- 다운로드/캐시는 서버와 동일한 CAS 레이아웃을 사용하고, 순차 읽기 시 다음 청크를 선반입(readahead)한다.

### FR-3 보안
- 모든 연결은 TLS 1.3 + mTLS로 보호한다. 인증 전 상태에서 처리 가능한 명령은 화이트리스트로 제한한다.
- 서버는 클라이언트가 보낸 해시를 신뢰하지 않고 받은 바이트를 **직접 재해싱해 검증**한다.
- 경로는 파일시스템 경로가 아닌 DB 트리로만 해석해 path traversal을 구조적으로 차단한다. 유니코드 정규화(NFC/NFD)를 처리한다.

### FR-4 무결성 & 신뢰성
- 모든 blob 쓰기는 tmp → fsync → rename으로 원자적으로 수행한다.
- GC는 유예 기간(grace period)을 두어 방금 올라온(아직 커밋 전) 청크를 지우지 않는다.
- `meta.db`는 단일 장애점이므로 자동 백업한다.

### FR-5 마운트 UX
- 메타데이터/청크 캐시(TTL + negative 캐시)로 `ls`·미리보기가 답답하지 않게 한다.
- rename-후-저장, 오래 열린 파일, 캐시 용량 초과, 업로드 실패 등 쓰기 경로의 실패 케이스를 모두 처리한다.

## 8. 비기능 요구사항

- **성능:** SSD 처리량(USB3 어댑터 ~350MB/s / NVMe HAT ~800MB/s) 범위에서 대용량(1GB+) 파일을 안정적으로 처리한다.
- **안정성:** 데몬이 죽어도 좀비 마운트가 남지 않도록 시그널 핸들러에서 Unmount한다. 서버는 systemd로 자동 재시작한다.
- **이식성:** CLI는 순수 Go로 크로스 컴파일 가능하게 유지한다. FUSE 바이너리(cgo 의존)는 별도 모듈로 분리해 OS별로 빌드한다.
- **운영 보안:** 서버는 전용 유저로 실행(root 금지), systemd `ProtectSystem=strict`, 페어링/연결 rate limit과 read/write 타임아웃을 둔다.

## 9. 성공 지표

- 워드/vim/TextEdit로 저장한 문서가 에러 없이 새 버전으로 반영된다(저장 실패율 0에 수렴).
- 마운트한 폴더를 열었을 때 `ls`·미리보기가 답답하지 않다(체감 지연 최소화).
- 보안·CLI가 완성된 시점부터 실제 문서를 파이에 두고 매일 사용한다.
- 최종적으로 "파인더에서 열고 고치고 저장"이 성립한다 = 구글 드라이브급 사용 경험 달성.

> 개발 순서·마일스톤·완료 조건(DoD)·일정·실행 리스크는 별도 실행 계획 문서(`PLAN.md`)에서 다룬다.

현재 범위에는 넣지 않지만, 계층 분리 덕분에 나중에 얹을 수 있는 것들이다.

| HTTP/REST 게이트웨이 | 웹 UI·모바일 접근의 전제 |
